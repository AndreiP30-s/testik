# Соответствие ЛР1 и ЛР2

## ЛР1

Первая работа уже принята преподавателем, её версия сохранена отдельно.
ЛР2 развивает её код: хранение в памяти заменено PostgreSQL, а консольный ввод — REST.
Это не повторная сдача отдельного консольного приложения ЛР1.

| Требование | Что есть в текущей версии |
|---|---|
| Spring и Maven | pom.xml, TechStoreApplication, Maven Wrapper |
| Собственные классы, интерфейсы, наследование | JPA-модели; интерфейсы сервисов и репозиториев; абстрактный User с AdminUser, ManagerUser, CustomerUser |
| Коллекции | List значений характеристик и камер; Map характеристик в DTO; Set правил; List снимков цен и задач ExecutorService |
| Добавление, поиск, удаление, вывод | CRUD в сервисах и REST; фильтрация через JPA; данные выдаются в JSON |
| Циклы, условия, строки | ProductRules, CharacteristicValidator, нормализация email, работа с характеристиками и снимками цен |
| Unit-тесты | Проверки правил, сервисов, REST, форм, ошибок и многопоточности |
| Многопоточность одной коллекции | ParallelPriceService обрабатывает List<PriceSnapshot> через ExecutorService; имена price-worker-N попадают в лог |
| Enum ролей и абстрактный User | UserRole и SINGLE_TABLE-наследование User; роли ADMIN, MANAGER, CUSTOMER |

Разделение властных полномочий HTTP-клиентов ещё не реализовано. В приведённом
задании ЛР1 требуется подготовить структуру ролей для дальнейших работ, а не
полноценную авторизацию. Ролевая структура есть.
TDD в задании указан как желательный подход; факт наличия тестов не доказывает,
что весь код писался по TDD.

## ЛР2

| Требование | Реализация |
|---|---|
| PostgreSQL | Официальный образ в Docker Compose, отдельный named volume |
| Схема БД | db/01-schema.sql, 02-java-support.sql, 03-reference-data.sql; выполняются при первом запуске контейнера |
| PgAdmin | Можно подключить установленный pgAdmin к localhost:5434, база/пользователь techstore, локальный пароль из Compose. Для защиты показать таблицы и связи в pgAdmin |
| MVC | model → repository → service/impl → controller; представление REST — JSON, вход и выход описаны DTO |
| Lombok | Применяется в JPA-моделях |
| Spring Data JPA | Репозитории наследуют JpaRepository; фильтры через Specification |
| Все операции CRUD | Создание, чтение, обновление и удаление товаров и пользователей; работа со справочниками |
| REST API для CRUD | Сохранены JSON-маршруты; формы — дополнительные HTTP-операции над теми же сервисами |
| REST API с фильтрами | Название, бренд, категория, диапазон цены, доступность; фильтры можно сочетать |
| @SpringBootTest без БД | Тестовый профиль отключает DataSource/JPA, репозитории подменяются @MockitoBean; отдельный тест проверяет отсутствие подключения |

Формы в Swagger не отменяют REST и не меняют модель MVC. Данные отправляются
HTTP-запросами application/x-www-form-urlencoded, проходят валидацию и попадают
в те же сервисы/JPA. Полный JSON API также сохранён.

## Общие требования и подготовка к сдаче

- var для типов в исходниках не используется.
- README описывает назначение системы, пакеты, запуск и API.
- Контроллеры, сервисы, проверки и репозитории разделены по обязанностям.
- Файлы GitHub Actions и .gitlab-ci.yml подготовлены. Удалённый pipeline пока не
  запускался, потому что публикация проекта не выполнялась.
- После публикации нужен успешный CI и открытый PR/MR до Approve преподавателя.
- Схема создавалась SQL-скриптами Docker, не ручными действиями в интерфейсе pgAdmin.
  Для буквального выполнения пункта про pgAdmin следует открыть там эту базу и
  продемонстрировать/сохранить ER-диаграмму; при требовании преподавателя выполнить
  скрипты через Query Tool в отдельной пустой базе.
- Наличие нужной редакции IntelliJ и установка pgAdmin — пункты подготовки окружения,
  их нельзя подтвердить одними Java-файлами.

Заказы оставлены в общей SQL-схеме для другого предмета. REST API заказов в
приведённом задании ЛР2 явно не требуется и в согласованный объём не включался.
