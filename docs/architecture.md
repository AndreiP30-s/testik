# Архитектура

## Обработка запросов

REST-контроллер принимает DTO, проверяет входные данные и вызывает сервис.
Сервис выполняет бизнес-операцию в транзакции и обращается к репозиториям Spring Data JPA.
Ответ возвращается как DTO в JSON. Ошибки обрабатывает `ApiExceptionHandler`.

Основные сервисы: `ProductService`, `UserService`, `ReferenceService`, `DiscountService`.
Реализации находятся в `service.impl`.

## Каталог

Общие поля товара хранятся в `Product`: артикул, название, бренд, категория,
цена и доступность. Артикул имеет тип `Integer` и выдаётся последовательностью PostgreSQL.
Цена хранится как `BigDecimal`.

Характеристики представлены записями `ProductSpecification`, связанными с товаром
и определением характеристики. Значения хранятся строками; определение содержит
тип значения и единицу измерения. `CategoryCharacteristic` задаёт разрешённые
характеристики категории. Категории фиксированы в перечислении и SQL-ограничении.

| Категория | Обязательные характеристики |
|---|---|
| SMARTPHONE | processor, ramGb, storageGb, screenDiagonalInches, frontCameraMp, batteryCapacityMah, supports5g |
| TABLET | processor, ramGb, storageGb, screenDiagonalInches, frontCameraMp, batteryCapacityMah, cellular |
| LAPTOP | processor, ramGb, storageGb, screenDiagonalInches, frontCameraMp, storageType |
| HEADPHONES | headphoneType, wireless, noiseCancelling, minFrequencyHz, maxFrequencyHz |

`ProductRules` проверяет требования категории: обязательные характеристики,
допустимые значения, диапазоны частот и наличие камер. `CharacteristicValidator`
проверяет разрешение характеристики для категории и тип значения по справочнику.
Пустые значения характеристик отклоняются.

Задние камеры хранятся в `RearCamera`. Типы: WIDE, ULTRA_WIDE, TELEPHOTO, MACRO.
Одинаковые модули описываются одной записью с количеством. Смартфоны и планшеты
должны иметь заднюю камеру; ноутбуки и наушники не содержат таких записей.

Фильтры товаров строятся через JPA `Specification<Product>` и объединяются
условием AND. Фильтрация и пагинация выполняются в базе данных.

## Пользователи

`User` — абстрактная сущность с наследниками `AdminUser`, `ManagerUser`, `CustomerUser`.
Стратегия `SINGLE_TABLE` хранит всех пользователей в `app_user`.
Столбец `role` определяет подкласс. Ключ пользователя — email.

Смена роли выполняется обновлением discriminator-столбца и очисткой persistence context,
чтобы следующее чтение загрузило нужный подкласс. Пароли хешируются BCrypt.
DTO ответов не содержит пароль и его хеш.

Для сущностей с назначаемым строковым ключом используется `AssignedIdEntity`,
реализующий `Persistable<String>`. Флаг новой записи позволяет Spring Data выбрать
вставку; после загрузки или сохранения он сбрасывается JPA callback-методом.

## Скидки

`DiscountService` сохраняет исходные цены в `discount_backup`, состояние скидки —
в `discount_state`. Строка состояния блокируется на время изменения цен.
Пока скидка действует, изменения каталога запрещены. Отмена восстанавливает
исходные цены, в том числе после перезапуска приложения.

`ParallelPriceService` рассчитывает цены через `ExecutorService` в потоках
`price-worker-N`. В рабочие потоки передаются неизменяемые `PriceSnapshot`,
содержащие артикул, название и цену. Результат представлен `PriceQuote`.
JPA-сущности обрабатываются и сохраняются сервисом в транзакции.

## Окружение

Docker Compose запускает PostgreSQL с постоянным volume и проверкой готовности.
Java-приложение запускается отдельно. SQL-скрипты создают схему при первой
инициализации базы; Hibernate проверяет её соответствие сущностям при запуске.
